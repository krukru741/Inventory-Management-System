# NestJS + Prisma API — Implementation Plan

## Stack

| Layer | Choice |
|---|---|
| Runtime | Node.js 24 |
| Framework | NestJS 10 |
| ORM | Prisma 5 (`db pull` from existing PostgreSQL schema) |
| Auth | `@nestjs/passport` + `passport-jwt` + bcrypt (pgcrypto-compatible) |
| Validation | `class-validator` + `class-transformer` |
| API Docs | `@nestjs/swagger` (auto-generated OpenAPI 3.1) |
| Config | `@nestjs/config` with `.env` + Joi schema validation |
| Logging | `@nestjs/common` Logger + Pino (via `nestjs-pino`) |
| Testing | Jest (unit) + Supertest (e2e) |

## Phase 1 — Foundation + Core Catalog (implement first)

### 1a. Project Scaffold & Infrastructure

#### [NEW] `api/` (NestJS project)
- `npx @nestjs/cli new api --package-manager npm --skip-git`
- Install all dependencies in one pass (see below)

#### [NEW] `api/prisma/schema.prisma`
- Run `prisma db pull` to introspect the 17 SQL migrations
- Add `@@map` directives to match table names
- Regenerate client: `prisma generate`

#### [NEW] `api/src/prisma/prisma.service.ts`
- Extends `PrismaClient`, implements `OnModuleInit` / `enableShutdownHooks`
- Exported as a global module so every feature module can inject it

#### [NEW] `api/src/config/`
- `app.config.ts` — PORT, NODE_ENV, API_PREFIX, CORS origins
- `database.config.ts` — DATABASE_URL
- `jwt.config.ts` — JWT_SECRET, JWT_EXPIRES_IN
- Joi schema validates all required vars on startup

#### [NEW] `api/src/common/filters/http-exception.filter.ts`
- Maps Prisma `P2002` (unique) → 409, `P2025` (not found) → 404, etc.
- Returns uniform `{ statusCode, message, error, timestamp, path }` envelope

#### [NEW] `api/src/common/interceptors/logging.interceptor.ts`
- Logs method, URL, status, and duration via Pino

#### [NEW] `api/src/common/interceptors/transform.interceptor.ts`
- Wraps all successful responses in `{ data, meta }` envelope

#### [NEW] `api/src/main.ts`
- Global `ValidationPipe` (whitelist, forbidNonWhitelisted, transform)
- Global exception filter
- Swagger setup at `/api/docs`
- Helmet + CORS

#### [NEW] `api/src/modules/auth/`

|---|---|

### 1c. Core Catalog Modules (all follow the same pattern)

Each module contains: `module.ts`, `controller.ts`, `service.ts`, `dto/create-*.dto.ts`, `dto/update-*.dto.ts`, `dto/query-*.dto.ts`.

#### Users module — `GET/PATCH /users/:id`, `GET /users` (admin only)
- Password change endpoint: `PATCH /users/:id/password`
- Cannot delete self

#### Categories module — `GET /categories`, `GET /categories/:id`, CRUD (admin/manager)
- Recursive tree query via Prisma's self-relation

#### Suppliers module — full CRUD + `GET /suppliers/:id/products`

#### Warehouses module — full CRUD + nested `GET /warehouses/:id/locations`

#### Products module
- `GET /products` with filters: `?category=`, `?sku=`, `?search=` (uses pg_trgm via raw query), `?lowStock=true`
- `GET /products/:id` with stock-by-location breakdown
- `POST /products`, `PATCH /products/:id`, `DELETE /products/:id` (soft delete via `is_active`)
- `GET /products/:id/movements` — ledger history
- Nested: `POST /products/:id/images`, `DELETE /products/:id/images/:imageId`
- Nested: `GET /products/:id/variants`, CRUD variants
- Nested: `GET /products/:id/suppliers`, link/unlink suppliers

#### Inventory module
- `GET /inventory` — paginated stock levels (wraps `v_stock_summary` view)
- `GET /inventory/low-stock` — wraps `v_low_stock_alerts` view
- `POST /inventory/adjust` — manual adjustment (posts a `stock_movements` row + updates cache atomically in a Prisma `$transaction`)

> [!IMPORTANT]
> Every write to `inventory` goes through a **Prisma `$transaction`** that inserts `stock_movements` first and then upserts `inventory`. The DB trigger is a safety net — not the primary path.

## Phase 2 — Transactional Modules

### Purchase Orders module — `api/src/modules/purchase-orders/`
- `POST /purchase-orders` → creates header + line items, status = `draft`
- `PATCH /purchase-orders/:id/submit` → status = `pending_approval`
- `PATCH /purchase-orders/:id/approve` → status = `approved` (manager/admin role)
- `POST /purchase-orders/:id/receipts` → creates `goods_receipt` + items; updates `received_qty`, inserts `stock_movements` (type = `receipt`), upserts `inventory` — all in one `$transaction`
- `GET /purchase-orders` with filters: `?status=`, `?supplier=`, `?dateFrom=`, `?dateTo=`
- `GET /purchase-orders/open` — wraps `v_open_purchase_orders` view

### Sales Orders module — `api/src/modules/sales-orders/`
- `POST /sales-orders` → creates header + items; reserves `inventory.reserved_qty` in `$transaction`
- `PATCH /sales-orders/:id/confirm`
- `POST /sales-orders/:id/shipments` → creates `shipment` + items; inserts `stock_movements` (type = `sale`), decrements `inventory.quantity` + `reserved_qty` in `$transaction`
- `GET /sales-orders/open` — wraps `v_open_sales_orders` view
- Returns/RMA: `POST /sales-orders/:id/returns`, `PATCH /returns/:id/restock`

### Stock Movements module — `api/src/modules/stock-movements/`
- `GET /stock-movements` with filters: `?product=`, `?location=`, `?type=`, `?from=`, `?to=`
- Thin read-only controller — all writes come through other modules' `$transaction` blocks
- Idempotency: service checks `idempotency_key` before inserting; returns existing row if already posted

## Phase 3 — Operations

### Transfers module — full lifecycle (`draft → in_transit → completed`)
- `POST /transfers/:id/dispatch` — posts `transfer_out` movements
- `POST /transfers/:id/receive` — posts `transfer_in` movements

### Cycle Counts module
- `POST /cycle-counts/:id/items/:itemId/count` — records `counted_qty`
- `POST /cycle-counts/:id/post-adjustments` — for each discrepancy, posts `cycle_count_adjustment` movement, sets `stock_movement_id` FK, sets `adjustment_posted = true` — all in one `$transaction`

### Returns module — RMA status transitions + restock logic

### Notifications module
- `GET /notifications` — inbox for current user
- `PATCH /notifications/:id/read`
- Background task (`@nestjs/schedule`) that polls alert rules against `v_low_stock_alerts` every 5 min and writes to the `notifications` outbox

## Phase 4 — Reports & Docs

### Reports module — `api/src/modules/reports/`
| Endpoint | Source |
|---|---|
| `GET /reports/stock-valuation` | FIFO/LIFO/WA computed from `stock_movements` layers |
| `GET /reports/stock-summary` | `v_stock_summary` |
| `GET /reports/low-stock` | `v_low_stock_alerts` |
| `GET /reports/turnover` | `stock_movements` aggregated by product + date window |
| `GET /reports/dead-stock` | Products with no outbound movement in N days |

All reports accept `?format=json` (default) or `?format=csv`.

### Swagger / OpenAPI
- Auto-generated from `@ApiTags`, `@ApiOperation`, `@ApiResponse` decorators
- Accessible at `/api/docs` in dev/staging; disabled in production

## Open Questions

> [!IMPORTANT]
> **Prisma shadow database**: Prisma needs a second database to diff migrations. For local dev this is fine (`DATABASE_URL` + `SHADOW_DATABASE_URL`). Do you have a second PG database available, or should we skip Prisma's migrate workflow and rely purely on our existing raw SQL migrations (using `prisma db pull` + `prisma generate` only, no `prisma migrate`)?

> [!IMPORTANT]
> **Email/SMS for notifications**: The notification outbox is modelled in the DB. Should Phase 3 wire up a real transport (e.g. Nodemailer/SendGrid for email, Twilio for SMS), or is in-app only sufficient for now?

> [!NOTE]
> **File uploads (product images)**: The `product_images` table stores `url`. Should the API handle image upload (to local disk or S3-compatible bucket) and return a URL, or will images be managed externally and the API only stores the URL?
